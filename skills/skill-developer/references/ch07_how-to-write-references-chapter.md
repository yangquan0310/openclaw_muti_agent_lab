# 如何撰写 references 章节

> 如何为技能撰写指南性章节，让代理在实际使用中遇到问题时能快速找到答案。

---

## 问题

### 为什么要写 references 章节？

SKILL.md 是技能的导航首页，references 是技能的**详细操作手册**。

代理在使用技能时遇到的具体问题，需要在 references 中找到答案：
- "CLI 怎么建？" → references
- "质量检查有哪些项？" → references
- "怎么更新到新版本？" → references

### 当前 references 的问题

| 问题 | 表现 |
|------|------|
| 文件割裂 | cli 有 standards + workflow 两个文件 |
| 命名混乱 | guide-writing-guide、standards-writing-guide、workflow-writing-guide 三个元文章 |
| 结构不统一 | 有的文件是方法论，有的是标准，有的是工作流 |
| 内容重复 | development-guide 和 development-workflow 有重叠 |

### 新框架：每章解决一个问题

新框架下，每个 references 文章都对应一个**实际问题**：

```
references/
├── ch01_how-to-develop-new-skill.md    # "如何开发技能？"
├── ch03_how-to-build-cli.md             # "CLI 怎么建？"
├── ch04_how-to-write-scripts.md         # "scripts 怎么写？"
├── ch02_how-to-check-quality.md         # "质量怎么检查？"
└── ...
```

## 方法论

### 四层结构

每章统一包含四个层次：

| 层次 | 回答的问题 | 内容特点 |
|------|------------|----------|
| **问题** | 为什么要知道这个？ | 场景描述、常见困惑 |
| **方法论** | 怎么思考这个问题？ | 决策框架、判断标准 |
| **工作流** | 具体怎么执行？ | 步骤、可执行命令 |
| **执行标准** | 做到什么程度算合格？ | 检查清单、通过条件 |

### 四层的选择原则

| 场景 | 需要的层次 |
|------|----------|
| "为什么要知道这个" | 必须有「问题」 |
| 第一次解决此问题 | 必须有「方法论」+「工作流」 |
| 重复执行此任务 | 「执行标准」即可 |
| 只需要检查对错 | 「执行标准」即可 |

**注意**：不是每章都需要四个层次全部包含。简单问题可以只有「问题」+「执行标准」。

### 三类文章 vs 四层结构

旧框架用后缀区分文章类型：
- `*-guide` = 方法论
- `*-standards` = 标准
- `*-workflow` = 工作流

新框架不再依赖后缀区分，而是**每章都是完整四层结构**。后缀只保留：
- `index.md` = 书籍目录（固定）
- `SKILL.md` = 技能定义（固定）

### 写作原则

| 原则 | 说明 |
|------|------|
| **回答问题，不复述结构** | 指南告诉代理"遇到 X 情况怎么办"，不是"这个技能有哪些文件" |
| **给出判断标准，不只给步骤** | 告诉代理"如何判断用 A 方法还是 B 方法" |
| **步骤可执行，不模糊** | 每个步骤都有具体命令，不是"然后做相应处理" |

## 工作流

### 撰写步骤

```
① 确定章节要解决的问题
     ↓
② 确定需要的层次（问题/方法论/工作流/执行标准）
     ↓
③ 撰写「问题」章节
     ↓
④ 撰写「方法论」章节（如果需要）
     ↓
⑤ 撰写「工作流」章节（如果需要）
     ↓
⑥ 撰写「执行标准」章节（如果需要）
     ↓
⑦ 检查：是否回答了实际问题？
```

### 步骤 1：确定章节要解决的问题

**好问题**：
- "CLI 怎么建？"
- "scripts 怎么写？"
- "质量检查有哪些项？"

**坏问题**：
- "如何写指南"（这是元问题，应该直接写指南）
- "开发流程是什么"（太宽泛，应该拆成更小的问题）

### 步骤 2：确定需要的层次

| 问题复杂度 | 需要的层次 |
|------------|------------|
| 新手第一次做 | 四层全部需要 |
| 有经验但易错 | 问题 + 方法论 + 执行标准 |
| 只需要检查对错 | 问题 + 执行标准 |

### 步骤 3-6：撰写各层

**「问题」章节的写法**：

```markdown
## 问题

### 为什么要知道这个？

{场景描述：代理在什么情况下会需要这个}

### 常见困惑

{列出 2-3 个代理常问的问题}

### 和 XXX 的区别

{如果容易与相邻问题混淆，解释边界}
```

**「方法论」章节的写法**：

```markdown
## 方法论

### 判断框架

{给出一个决策树或判断条件}

### 示例

{2-3 个具体例子，解释如何判断}
```

**「工作流」章节的写法**：

```markdown
## 工作流

### 步骤 1：{具体步骤}

{具体命令}

### 步骤 2：{具体步骤}

{具体命令}

### 判断：如果 {条件}
→ 走 A 路径
→ 否则走 B 路径
```

**「执行标准」章节的写法**：

```markdown
## 执行标准

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | {具体检查项} | {什么算通过} |
| 2 | {具体检查项} | {什么算通过} |
```

## 执行标准

### 结构标准

| 标准 | 要求 |
|------|------|
| 文件名 | 与解决的问题一致，如 `ch03_how-to-build-cli.md` 对应"CLI 怎么建" |
| 四层结构 | 根据需要包含，不强制四层全有 |
| 标题层级 | `## 问题`、`## 方法论`、`## 工作流`、`## 执行标准` |

### 内容标准

| 标准 | 要求 |
|------|------|
| 回答实际问题 | 代理看到能直接知道怎么做 |
| 步骤可执行 | 每步都有具体命令或操作 |
| 判断标准明确 | 不模糊，如"合理"→"行数 ≤ 200" |
| 无重复内容 | 不与相邻章节重叠 |

### 反面案例

**❌ 问题写成流程**：
```markdown
## 问题

### 步骤 1：安装依赖
### 步骤 2：配置
```

**✅ 问题写成场景**：
```markdown
## 问题

### 什么时候需要 CLI？

当技能需要被 cron、其他脚本、或外部技能调用时。
```

**❌ 方法论写成步骤**：
```markdown
## 方法论

### 第一步：确定模块数量
### 第二步：创建 main.py
```

**✅ 方法论写成判断框架**：
```markdown
## 方法论

### 如何判断需要多模块还是单模块？

| 判断条件 | 类型 |
|----------|------|
| 业务功能 ≥ 2 个独立模块 | 多模块 |
| 业务功能只有 1 个 | 单模块 |
```

**❌ 工作流写成原理**：
```markdown
## 工作流

### CLI 的设计原则

CLI 应该遵循 Unix 哲学...
```

**✅ 工作流写成步骤**：
```markdown
## 工作流

### 步骤 1：明确 CLI 结构

确定命令格式：`{技能名} {模块} [参数...]`
```

**❌ 执行标准写成教程**：
```markdown
## 执行标准

### 如何检查 SKILL.md？

1. 打开文件
2. 检查是否有 YAML frontmatter
3. 检查 name/description/version 是否存在
```

**✅ 执行标准写成检查清单**：
```markdown
## 执行标准

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | SKILL.md 有 YAML frontmatter | name/description/version 存在 |
| 2 | SKILL.md 正文不超过 200 行 | 行数 ≤ 200 |
```

---

## 检查清单

撰写完成后检查：

- [ ] 文件名是否对应一个实际问题？
- [ ] 「问题」章节是否解释为什么要知道这个？
- [ ] 「方法论」章节是否给出判断框架而非步骤？
- [ ] 「工作流」章节是否每步都有具体命令？
- [ ] 「执行标准」章节是否原子化、无歧义？
- [ ] 是否与相邻章节有内容重复？
- [ ] 代理遇到实际问题是否能直接找到答案？
