## 二、逐项审计

### A. 中文表达质量（27 / 30）

#### 优点

1. **"一句话定位"段（line 7-9）是全篇最佳**：
   > "老板（杨权）研究工作的全流程数字助手：从'想研究一个问题'到'产出一篇可投稿的学术文章'，中间每一步都有自动化/半自动化支持。"
   
   - 完整表达"角色 + 工作范围 + 价值主张"——15 秒内让读者知道这是什么 / 给谁用 / 解决什么
   - 类比 "从 A 到 B" 句式自然，符合 README 标准开头范式

2. **"三联动"概念用表格表达准确**：
   | 角色 | 载体 | 职责 |
   |------|------|------|
   | **wiki** | 知识沉淀层 | 存 source/synthesis/concept |
   
   - 角色 / 载体 / 职责三列清晰，"知识沉淀层 / 文献数据库 / 附件存储层" 三个名词短语平行工整

3. **ASCII 数据流总览段（line ~60-130）**——用 `┌─┐` 框 + 6 阶段对应 6 模块，**视觉化最成功的段**：
   - 框内 6-9 字短句表达 1 件事
   - 阶段箭头清晰：`阶段1 → 阶段2 → ... → 阶段6`

4. **版本历史段（line ~210-247）**——3 条最新版本（v6.0.4 / v6.0.5 / v6.0.6）用 `🔴 🟡 🟢` 严重度图标 + 编号子项，**变更粒度合适、可追溯**。

#### 问题

1. **"七大核心功能"表头表述不精确**：
   - 表头"按老板 2026-06-23 拍板的指令顺序"
   - 表格里"功能 / 现状 / 入口命令 / 沉淀位置" 4 列
   - 但**功能 #7 是"文章排版"——不是 CLI 命令**，入口是"手工调 quarto render"
   - 表格里"现状"列都用 `✅ vX.Y.Z+` 前缀——这是文档规范的优点，但表头写"按老板拍板"显得过度修饰
   - 建议：表头删除"按老板拍板的指令顺序"，改为"按文档章节顺序"

2. **"进一步开发方向"段（line ~190-210）表格 + emoji + 嵌套子标题** 略乱：
   - H3 `### 🔴 紧急（v6.0.0 必须解决）`
   - H3 `### 🟡 中等（v6.1.0-v6.5.0）`
   - H3 `### 🟢 长期（v7.0.0+）`
   - 每个 H3 下又有 1 个表 + 1 行 emoji + 1 句解释
   - "缺口 / 现状 / 目标"3 列——但行的"现状"列出现"✅ 已完成"——**和"缺口"段定位矛盾**
   - 建议：要么改名"已完成变更记录"（删除"缺口"两字），要么真放待办（删除 ✅）

3. **"边界条件"表 4 行（line ~155-165）**：
   - ✅ / ❌ / ❌ / ⚠️ 4 行
   - 但 ❌ 行写"不做" / "不负责"——两个否定词不同含义
   - "⚠️ 边界条件"行说明"任一缺失 = 数据漂移"——但前 3 行没说这是 wiki↔Zotero↔WebDAV 联动边界
   - 建议：表头加 1 行小字"所有边界围绕 wiki↔Zotero↔WebDAV 三联动"

4. **环境变量段（line ~170-180）**——6 个变量用表：
   - 但"DEEPSEEK_API_KEY / KIMI_API_KEY / TOKENHUB_API_KEY" 一行里塞 3 个变量
   - "❌ ZOTERO_GROUP_ID" 表"可选"——但"可选"含义不清：是"用户可选"还是"场景可选"
   - 建议：3 个 LLM KEY 各占一行 / "可选"列改为"场景"列（说明何时需要）

#### 改进建议

- "七大核心功能"表头简化，删除"按老板拍板的指令顺序"
- "进一步开发方向"段重命名为"已完成变更亮点"（更准确反映 ✅）
- "边界条件"加 1 行小字说明上下文
- "环境变量"3 个 LLM KEY 各占一行

3. **数据流 ASCII 总览**——1 张图替代 200 字说明

   ```
   ├── apaquarto-manuscript-guide.md ← 严格 APA 7 manuscript 完整配置
   ├── module-{search,manage,...}.md
   ├── narrative-review-guide.md     ← 叙述性综述撰写指南
   ├── meta-analysis-guide.md        ← 元分析撰写指南
   ├── observational-study-guide.md  ← 观察研究报告撰写指南
   ```

   - 建议：命令注释移到末尾"已废弃命令"段（如果有的话），命令块只保留可用命令

3. **"边界条件" / "环境变量" 两段可合并**——都描述"系统边界 / 依赖"，但分两个表：
   - 边界条件 4 行 / 环境变量 6 行——加 1 段话总共 < 20 行
   - 建议：合并为"边界与依赖"段，先表后文

- "目录结构"删除注释行（与 SKILL.md 指南导航表保持一致）
- "快速开始"命令块去除版本历史注释

### C. 结构清晰度（16 / 20）

#### 优点

1. **章节顺序符合 README 标准范式**：
   - 标题 → 一句话定位 → 三联动架构 → 七大功能 → 数据流 → 目录结构 → 快速开始 → 边界 / 环境 → 开发方向 → 版本历史
   - 新人 5 分钟内能找到任何一段

2. **H2 标题用名词短语**（无"概览" / "其他"），H3 用 "🔴 紧急" 等带状态标识——视觉分层清晰。

3. **每个 H2 段下都有 1 张表 / 1 段图 / 1 段列表**——形式稳定。

#### 问题

1. **"目录结构"段（line 138-159）层级混乱**：
   - `research-assistant/` 下是 4 个子目录（scripts / references / assets / _meta.json）
   - `scripts/` 下 7 个子目录（main.py + config.json + 7 子目录）
   - `references/` 下 18 个文件——**但目录树只画了 16 个**（缺 `index.md` / `research-workflow.md` 两行——SKILL.md 指南导航里有，README 目录树里被合并到 `module-{...}.md` 那一行）
   - 实际 assets/ 列出 8 个模板——但 SKILL.md 模板资源段说 11 个模板——**目录树与 SKILL.md 不一致**

2. **"快速开始"段标题 `8 条命令`——但下面列出 6 个 block（含 1 段说明）**：
   ```
   # 1. 检索文献
   # 2. 收录到 Zotero
   ...
   # 6. 三方一致性检查
   ```
   - **6 个 block 不是 8 条**——标题数字对不上
   - 实际每个 block 含 1-2 行命令，总命令数 = 12 条
   - 建议：标题改"常用命令"（去掉"8 条"具体数字）

3. **"边界条件"段 4 行表格 + "环境变量"段 6 行表格 + "进一步开发方向" 段 3 个 H3 子表**——4 张表 + 2 张表 = **6 张表**堆在后半段——视觉密度过高：
   - 建议：合并"边界 / 环境" → 1 张表；"开发方向"留作 1 张表

#### 改进建议

- "目录结构"补 `references/index.md` / `references/research-workflow.md` 两行；assets 模板数与 SKILL.md 模板资源段对齐（11 个）
- "快速开始"标题改"常用命令"，去数字
- 后半段表数量从 6 张压缩到 3 张

### D. 一致性（13 / 20）

#### 关键不一致点

1. **模块数 vs SKILL.md 不一致**：
   - README 七大核心功能 = 检索 / 保存到 Zotero / 管理 WebDAV / 管理 wiki / 精读 / 攥写 / 排版 = **7 项**
   - SKILL.md 7 模块 CLI = search / download / upload / summarize / synthesize / manage / maintain = **7 个 CLI 模块**
   - **README 的"管理 WebDAV 附件"是 download 模块内嵌功能——在 SKILL.md 不算独立模块**
   - **README 的"排版"不是 CLI——在 SKILL.md 不在 7 模块清单**
   - 结论：两边的"7"定义不一致。README 的"7"是"用户视角功能"，SKILL.md 的"7"是"CLI 模块"

2. **"进一步开发方向"段标题 vs 内容不一致**：
   - 标题叫"进一步开发方向（v6.0.0+）"
   - 但内容是"已完成的变更记录"（"README 与 SKILL.md 不一致 ✅ 已完成" / "drift-graph 三方联动可视化 ✅ 已完成" / "多模态精读 ✅ 已完成（v6.0.2）"）
   - **标题说"开发方向"，内容却是"已完成"——严重不一致**

3. **"七大核心功能"中 upload 行与 SKILL.md 不一致**：
   - README: `🆕 v6.0.3+ 本地 PDF 反向上传`
   - SKILL.md: upload 是 7 模块之一，不是"🆕 加号项"
   - **README 把 upload 当"额外加号项"，SKILL.md 当"核心模块"**

4. **"边界条件"段 README 与 SKILL.md 不一致**：
   - README: 4 行（✅ 能做 / ❌ 不能做 / ❌ 不负责 / ⚠️ 边界条件）
   - SKILL.md: 2 行（✅ 能做 / ❌ 不能做）
   - **README 比 SKILL.md 多 2 行**——SKILL.md 没同步 README 的细化

5. **"快速开始"命令数不一致**：
   - README: 标题"老板最常用的 8 条命令"，实际 6 个 block / 12 行命令
   - SKILL.md: "快速调用"无标题数字，命令数 = 13 行
   - **两边都没真正"8 条"**

#### 改进建议

- README 与 SKILL.md 顶部加 1 张"模块对照表"——明确两边"7"的不同定义
- "进一步开发方向"改名"v6.0.0+ 已完成变更亮点"——内容与标题一致
- upload 在 README 七大功能表里升级为"功能 7"，去掉"🆕"符号（已是稳定功能）
- 边界条件 SKILL.md 同步 README 的 4 行细化

### E. 用户友好度（9 / 10）

#### 优点

1. **"一句话定位"段 + "三联动"段** 是最佳新人入口——30 秒读懂 skill 是什么。
2. **"七大核心功能"表 1 屏可读**——知道 skill 能做什么。
3. **"快速开始"段命令可复制即用**——`python3 scripts/main.py <module> <args>` 模板稳定。

1. **"快速开始"标题"老板最常用的 8 条命令"**——数字不准 + "老板最常用"对 LLM 视角不重要（README 主受众是"老板本人"但实际读者也是其他 owner / reviewer）。

- "老板最常用的 8 条命令" → "常用命令"
