# 程序项目

> 多代理协作完成程序从需求分析到部署维护的全流程。
> 以 `agent-self-development` 项目为生产实际参照。

---

## 协作角色

程序项目由 **3 个角色** 协作完成，非线性执行：

| 角色 | 职责范围 | 核心产出 |
|------|---------|---------|
| **PM（产品经理）** | 需求分析 + 架构设计 + 进度管理 | 需求清单、路线图、任务分配 |
| **Developer（程序员）** | 代码实现 + 测试验证 + 文档同步 | 源码、测试报告、文档更新 |
| **Reviewer（审查员）** | 代码审查 + 合规检查 + 裁决 | 审查报告、批准/拒绝 |

**大管家**：仅负责创建目录、维护 `metadata.json`、版本归档，不参与技术决策。  
**用户**：提供初始需求，最终验收确认 `[APPROVED]`。

## 项目目录结构

```
程序项目/
├── README.md              # 项目总览（人类视角）
├── metadata.json          # 机器可读架构（含角色定义）
├── openclaw.plugin.json   # 插件配置（如适用）
├── package.json           # 依赖配置
├── .gitignore             # 版本控制忽略
│
├── agents/                # 多 Agent 角色定义
│   ├── product-manager.md
│   ├── developer.md
│   └── reviewer.md
│
├── src/                   # 源代码
├── test/                  # 测试套件
├── skills/                # 项目级技能
│
├── docs/
│   ├── roadmap/           # 版本路线图（v{x.y.z}.md）
│   ├── changelog/         # 变更日志
│   ├── reference/         # 技术参考文档
│   ├── reports/           # 测试报告 + 审查报告
│   │   ├── test-YYYY-MM-DD-HH-mm-ss.md
│   │   └── review-YYYY-MM-DD-HH-mm-ss.md
│   └── cases/             # 案例文档
│
├── logs/                  # 运行日志
└── .agent/                # 元数据层（隐藏目录）
    ├── events/            # 事件流
    ├── locks/             # 并发控制
    ├── decisions/         # 决策存档
    ├── tasks/             # 任务索引
    └── agents/            # 项目级代理角色规范
        ├── product-manager.md
        ├── developer.md
        └── reviewer.md
```

## 协作流程

### 阶段 1：PM 定义需求与架构

```
用户输入需求
  → PM 需求澄清 → 输出需求清单
  → PM 架构设计 → 输出 docs/roadmap/v{x.y.z}.md
  → PM 任务规划 → 写入 TODO.md，分配 Developer
```

### 阶段 2：Developer 实现

```
读取路线图/任务分配
  → 技术方案（复杂任务先输出简要方案）
  → 代码实现（按编码规范）
  → 测试验证（npm test）
  → 文档同步（[DOC_UPDATE] 或 [DOC_SKIP]）
  → 提交审查（附测试报告 docs/reports/test-*.md）
```

### 阶段 3：Reviewer 审查

```
Developer 提交代码 + 测试报告
  → 读取 TODO.md 确认审查范围
  → 代码审查（逐文件逻辑审查）
  → 合规审查（对照规范红线）
  → 测试审查（独立运行 npm test 验证）
  → 裁决
      ├── 无 blocker → [APPROVED]
      ├── 有 warning → [CONDITIONAL_APPROVED: 修复项]
      └── 有 blocker → [REJECTED: 理由]
  → 输出审阅报告 docs/reports/review-*.md
```

### 阶段 4：循环修复（如需要）

```
Developer 修复 → [FIXED: 问题描述]
  → Reviewer 独立重审（不采信 [FIXED] 标记）
  → 裁决 → [APPROVED] / [REJECTED]
```

### 阶段 5：PM 验收与 Git 归档

```
Reviewer [APPROVED]
  → PM 对照验收标准确认完成
  → 更新 README + metadata.json
  → 输出 docs/changelog/v{x.y.z}.md
  → Git 版本控制：development 分支日常提交，完成整体时合并到 main
```

## 核心文件

| 文件 | 职责 | 维护者 |
|------|------|--------|
| `README.md` | 项目名片：名称、类型、目的 | PM |
| `metadata.json` | 机器可读架构、角色定义、版本信息 | PM |
| `TODO.md` | 任务状态、进度看板 | PM |
| `agents/*.md` | 角色定义、职责边界、工作流 | PM |
| `docs/CONVENTIONS.md` | 编码规范、钩子合规红线 | PM / Reviewer |
| `docs/COLLABORATION.md` | 协作协议、标记规范 | PM |

---

## Git 工作流

| 分支 | 用途 | 推送时机 |
|------|------|---------|
| `main` | 稳定版本，已发布功能 | **完成整体任务时** |
| `development` | 日常开发，功能迭代 | **完成阶段子任务时** |

**Commit 格式**：`{类型}: 简要说明`

| 类型 | 使用场景 |
|------|---------|
| `feat` | 新增功能 |
| `fix` | 修复问题 |
| `docs` | 文档更新 |
| `refactor` | 代码重构 |
| `test` | 测试相关 |
| `chore` | 构建/工具 |

## 👥 Agent 角色速查

| 角色 | 核心职责 | 可操作目录 | 禁止事项 |
|------|----------|-----------|---------|
| **产品经理** | 需求分析、架构设计、任务分配 | 全局 | 不写代码 |
| **程序员** | 代码实现、测试验证、文档同步 | `src/`、`test/` | 不决定产品方向 |
| **审查员** | 代码审查、合规检查、裁决 | `src/`（只读） | 不修改代码 |

## 标记体系

### Developer → Reviewer

| 标记 | 含义 |
|------|------|
| `[DOC_UPDATE: 文件]` | 代码变更需同步文档 |
| `[DOC_SKIP]` | 本轮变更无需更新文档 |
| `[TECH_BLOCKER]` | 发现技术不可行，需 PM 调整架构 |
| `[TEST_PASS]` | 测试全部通过 |
| `[TEST_FAIL: 原因]` | 测试失败 |

### Developer → Reviewer（修复后）

| 标记 | 含义 |
|------|------|
| `[FIXED: 问题]` | 已修复 Reviewer 提出的问题 |
| `[DISCUSS: 理由]` | 对审查意见有异议 |

### Reviewer 裁决

| 标记 | 含义 |
|------|------|
| `[APPROVED]` | 审查通过 |
| `[CONDITIONAL_APPROVED: 条件]` | 有条件通过 |
| `[REJECTED: 理由]` | 审查未通过 |
| `[BLOCKER]` | 严重问题，必须修复 |
| `[WARNING]` | 潜在问题，建议修复 |
| `[SUGGESTION]` | 改进建议，非强制 |

### PM 标记

| 标记 | 含义 |
|------|------|
| `[ARCH_APPROVED]` | 架构确认，Developer 可以开始实现 |
| `[SCOPE_CHANGE]` | 需求范围发生变更 |
| `[RISK]` | 识别到风险 |
