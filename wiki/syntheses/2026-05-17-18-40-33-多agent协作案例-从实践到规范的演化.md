# 从学生论文修改到项目管理体系的演化

> **核心问题**：三个管理技能（thesis-manager / course-manager / program-manager）从何而来？
> **答案**：从**学生论文修改项目**的真实协作实践中抽象而来。

---

## 一、起源：学生论文修改项目（2026-05-09）

### 实践背景

用户将一篇学生论文的修改任务分配给实验室，由多个 Agent 协作完成。这是实验室**首次大规模多 Agent 协作实践**，后续所有项目管理体系均源于此。

### 参与角色

| 角色 | Agent ID | 职责 | 协作方式 |
|------|----------|------|----------|
| **心理专家** | psychologist | 文献综述 + 讨论初稿 | 完成自己部分后"举手"请求协作 |
| **写作专家** | writer | 整合全文 + 变量修正 | 接收 psychologist 产出，多轮修正 |
| **审稿助手** | reviewer | 全文审核 + 审稿意见 | 发现 🔴 问题 → 返回 writer 修正 |
| **大管家** | steward | 文件归档 + 版本管理 | 最终交付物归档、云文档上传 |

### 协作流程（五阶段）

```
阶段1：用户分配任务 → psychologist
阶段2：psychologist 完成 → 举手"需要 writer 整合" → 用户协调分配
阶段3：writer 执行（Fix-R1/R2/R3/R5 多轮修正）
阶段4：reviewer 审核（8项检查清单）→ 发现 🔴 问题 → 返回修正
阶段5：steward 归档（终稿 → manuscripts/ → 云文档）
```

### 关键协作机制（三项创新）

#### 创新1：TODO.md 进度看板

```markdown
# TODO.md

## 任务追踪表
| 任务 | 状态 | 负责人 | 来源 |
|------|------|--------|------|
| 文献综述 A1 | ✅ | psychologist | 用户分配 |
| 全文整合 | ⏳ | writer | psychologist 举手请求 |
| 审稿审核 | ⬜ | reviewer | writer 完成触发 |

## 举手请求
- [ ] "我擅长文献综述，但全文整合需要写作专家。建议分配给 writer。"
```

**设计原则**：
- 所有 Agent 通过**同一进度看板**了解全局状态
- 任务状态流转：⬜ 待办 → ⏳ 进行中 → 🔍 待确认 → ✅ 已完成
- 完成者标记进度，不干涉其他 Agent 的具体执行

#### 创新2：举手请求协议

```
psychologist 发现需要 writer
  → 在 TODO.md「待分配」写入：
    "我擅长X，但需要Y。建议分配给擅长Y的Agent。"
  → 向用户汇报
  → 用户协调后分配新 Agent
  → 新 Agent 读取 TODO.md 了解上下文
```

**核心规则**：Agent 只能请求协助，不能干涉具体如何完成。

#### 创新3：审核闭环机制

```
reviewer 执行 8 项审核清单
  → 发现 🔴 严重问题
  → 返回原 Agent 修正
  → 修正后重新审核
  → 无 🔴 → 交付 steward 归档
```

## 二、演化：从单次实践到可复用规范

### Step 1：TODO 模板标准化

将学生论文修改中的 TODO.md 实践经验，提炼为**通用项目进度看板模板**：

```
学生论文修改 TODO.md
    ↓ 抽象通用结构
syntheses/（TODO 模板规范）
    ↓ 适配不同项目类型
thesis-manager/references/TODO模板.md（论文项目专用）
course-manager/SKILL.md 中的 TODO 章节（课程项目专用）
```

**通用化内容**：
- 任务追踪表（优先级 / 负责 Agent / 状态）
- 任务树（多级子任务、来源、产出、注意事项）
- 维护日志（时间 / 操作 / 执行者）
- 代理协作原则（只能请求、不能干涉）

### Step 2：创建 .agent 元数据层

学生论文修改实践的教训：
> "缺少 .openclaw/ 元数据层，无 events/、tasks/、locks/ 结构化记录"

演化出 **.agent 目录结构**：

```
项目根目录/
├── .agent/                    # 元数据层（隐藏目录）
│   ├── events/                # 事件流（每次操作自动记录）
│   ├── locks/                 # 并发控制（防止多 Agent 冲突）
│   ├── decisions/             # 决策存档（重要决策记录）
│   └── tasks/                 # 任务索引（与 TODO.md 同步）
```

**作用**：
- 机器可读的协作记录
- 支持 agent-self-development 插件的状态追踪
- 实现自动化流转（审核发现问题 → 自动返回修正）

### Step 3：开发 agent-self-development 插件

从"人工管理 TODO.md"演化为"插件自动记录 + Agent 自主决策"：

```
人工阶段（学生论文修改）
  → Agent 手动更新 TODO.md
  → 用户手动协调任务分配
  → steward 手动归档版本

插件阶段（agent-self-development v4.0.0+）
  → 插件通过 Hook 自动注入 skill（planning/monitoring/development）
  → Agent 自主调用 Tool（create_plan / record_deviation / advance_phase）
  → 事件文件自动记录（.agent/events/）
  → 状态机自动流转（draft → active → completed）
```

**插件架构**：
- **元认知层**：计划（Plan）→ 监控（Deviation）→ 调节（Attribution）
- **工作记忆层**：文件系统上下文管理、任务文件索引
- **人格发展层**：任务完成后分析同化/顺应，更新人格文件
- **项目上下文层**：Tool 暴露 + 最小化 Hook 注入

### Step 4：三个管理技能的诞生

从单一论文项目，抽象出**三种项目类型的管理规范**：

| 演化路径 | 来源 | 产物 |
|----------|------|------|
| 学生论文修改 → 博士论文 → 期刊论文 | thesis-manager | **论文项目管理技能** |
| 论文修改中的多人协作 → 课程备课五人组 | course-manager | **课程项目管理技能** |
| agent-self-development 插件开发实践 | program-manager | **程序项目管理技能** |

### program-manager 的演化

program-manager 的诞生路径不同于前两个：
- **不是**从论文/课程协作中抽象
- **而是**从 `agent-self-development` **插件开发实践**中总结

agent-self-development 插件（v4.0.0+）本身是一个**程序项目**，由 programmer 主导开发。在开发过程中，形成了 PM → Developer → Reviewer 的三角色协作模式，随后被抽象为 program-manager 技能。

**关键特征**：
- PM 负责需求分析 + 架构设计（输出 roadmap）
- Developer 按 TODO 编码 + 测试（npm test）
- Reviewer 独立审查 + 裁决（[APPROVED]/[REJECTED]）
- 使用 Git 双分支（dev/main）管理版本
- Commit 格式：`{类型}: 简要说明`（feat/fix/docs/refactor/test/chore）

## 三、三个管理技能与 TODO 模板的关系

```
syntheses/（通用模板）
    ├── thesis-manager/SKILL.md 中的 TODO 章节
    │   └── 论文项目：文献综述 → 写作 → 审稿 → 归档
    ├── course-manager/SKILL.md 中的 TODO 章节
    │   └── 课程项目：v1需求 → v2框架 → v3前沿 → v4课件 → v5审校 → v6终稿
    └── program-manager/SKILL.md
        └── 程序项目：PM需求 → 架构设计 → 编码开发 → QA审查 → 验收归档
```

**共同点**：
- 均使用 TODO.md 作为**进度看板**
- 均遵循"Agent 举手请求 → 用户协调分配"的协作协议
- 均支持多轮修正（论文：Fix-R1/R2/R3；课程：v1→v6；程序：需求→架构→编码→QA）
- 均通过 .agent/ 元数据层记录事件和状态

## 四、关键经验总结

### 成功要素

1. **TODO.md 驱动一切**：从单次论文修改到三种项目类型，TODO.md 是核心协作载体
2. **举手不阻塞**：Agent 完成自己部分后再请求协作，不等待、不空转
3. **审核闭环**：reviewer 的 8 项审核清单 → 程序项目的 QA 审查 → 课程项目的督导审校
4. **插件赋能**：从人工管理到 agent-self-development 自动记录，释放大管家精力

### 演化脉络

```
2026-05-09  学生论文修改（首次实践）
    ↓ 抽象 TODO 模板
2026-05-10  syntheses/（通用模板）
    ↓ 创建 .agent 目录 + 开发插件
2026-05-08  agent-self-development v4.0.0（项目上下文层）
    ↓ 适配论文项目
2026-05-09  thesis-manager v2.0.0（论文项目管理）
    ↓ 适配课程项目
2026-05-11  course-manager v2.0.0（课程项目管理）
    ↓ 适配程序项目
2026-05-12  program-manager v1.0.0（程序项目管理）
```
