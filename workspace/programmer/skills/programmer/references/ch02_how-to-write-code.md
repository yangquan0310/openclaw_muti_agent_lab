# 如何编写代码

> 命名规范、注释规范、代码结构、整洁代码原则。

---

## 问题

### 什么是好代码？

| 维度 | 好代码 | 坏代码 |
|------|--------|--------|
| 可读性 | 他人能理解 | 只有自己能懂 |
| 可维护性 | 改起来容易 | 改一处坏三处 |
| 可测试性 | 容易写测试 | 无法测试 |

### 核心原则

> **代码是写给人看的，顺便给机器运行**

## 方法论

### 命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 变量 | snake_case | `user_name`, `is_valid` |
| 函数/方法 | snake_case，动词开头 | `get_user()`, `validate_input()` |
| 类 | PascalCase | `UserService`, `OrderManager` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 包/模块 | 全小写 | `utils`, `auth` |

### 函数设计原则

| 原则 | 说明 |
|------|------|
| **单一职责** | 一个函数只做一件事 |
| **短小** | 理想 < 20 行 |
| **参数少** | 理想 < 3 个 |
| **无副作用** | 相同输入 → 相同输出 |

## 工作流

### 步骤 1：命名

1. 变量名要描述它包含什么
2. 函数名要描述它做什么
3. 类名要描述它是什么

### 步骤 2：写函数

1. 先写函数签名
2. 再写实现
3. 检查是否单一职责

### 步骤 3：写注释

| 需要注释 | 不需要注释 |
|----------|------------|
| 为什么这么做 | 代码本身能说明的 |
| 复杂逻辑 | 明显的逻辑 |
| 业务规则 | 追踪变更（用 git） |

### 步骤 4：重构

1. 识别坏味道
2. 小步改进
3. 验证测试通过

## 执行标准

### 代码检查清单

- [ ] 变量命名有意义
- [ ] 函数名描述行为
- [ ] 类名是名词
- [ ] 无过长函数（> 50 行需重构）
- [ ] 无重复代码
- [ ] 测试覆盖核心逻辑
