# 如何设计架构

> 分层架构、微服务、设计模式、技术选型。

---

## 问题

### 什么时候需要架构设计？

| 场景 | 是否需要 |
|------|----------|
| 新项目 | ✅ 必须 |
| 新模块（影响范围大）| ✅ 必须 |
| Bug 修复 | ❌ 不需要 |
| 小功能 | ❌ 不需要 |

### 架构的目标是什么？

| 目标 | 说明 |
|------|------|
| **可维护** | 改起来容易，不影响其他模块 |
| **可扩展** | 加新功能不需要改老代码 |
| **可测试** | 单元测试容易写 |
| **可部署** | 独立部署，不相互影响 |

## 方法论

### 常见架构模式

| 模式 | 适用场景 | 复杂度 |
|------|----------|--------|
| **分层架构** | 一般应用 | 低 |
| **MVC** | Web 应用 | 低 |
| **微服务** | 大型系统 | 高 |
| **CQRS** | 读写分离场景 | 中 |
| **DDD** | 复杂业务逻辑 | 高 |

### 分层架构

```
┌─────────────────┐
│    Controller   │  ← 处理请求
├─────────────────┤
│     Service     │  ← 业务逻辑
├─────────────────┤
│   Repository    │  ← 数据访问
├─────────────────┤
│      Model      │  ← 数据模型
└─────────────────┘
```

### SOLID 原则

| 原则 | 说明 |
|------|------|
| **S** 单一职责 | 一个类只有一个变化原因 |
| **O** 开闭原则 | 对扩展开放，对修改关闭 |
| **L** 里氏替换 | 子类可替代父类 |
| **I** 接口隔离 | 接口要小而专 |
| **D** 依赖反转 | 依赖抽象，不依赖具体 |

## 工作流

### 步骤 1：识别模块

1. 按业务领域划分模块
2. 确定模块边界
3. 定义模块间依赖

### 步骤 2：定义接口

1. 确定模块提供的接口
2. 明确接口的输入输出
3. 记录接口契约

### 步骤 3：选择技术栈

1. 语言/框架
2. 数据库
3. 缓存
4. 消息队列

### 步骤 4：画架构图

1. 组件图
2. 部署图
3. 数据流图

### 架构检查清单

- [ ] 模块划分清晰

- [ ] 无循环依赖
- [ ] 技术选型有依据
