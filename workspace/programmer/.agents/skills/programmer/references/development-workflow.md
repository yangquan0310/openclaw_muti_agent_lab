# 开发流程

> 从需求到交付的核心原则。

---

## 核心原则

### 理解全貌再动手

改代码前先理解上下文和影响范围。不确认不编码。

### 蓝图先于实现

架构设计完成、接口明确后再编码。没有图纸不施工。

### 接口即契约

模块间通过清晰接口协作，降低耦合。改内部实现不影响外部。

### 小步提交

每次只改一件事，频繁验证。commit 早而小。

---

## 判断框架

### 什么时候需要技术设计？

| 场景 | 决策 |
|------|------|
| 新项目/新模块 | 必须设计 |
| 修改核心逻辑 | 必须设计 |
| 多人协作 | 必须设计 |
| Bug 修复 | 可跳过 |
| 小改动 | 可跳过 |

### 什么时候不需要详细设计？

- 单个函数/类的简单改动
- 明显的重构（rename、format）
- 测试代码补充
- 文档更新

---

## 常见错误

| 错误 | 后果 |
|------|------|
| 不理解需求就动手 | 返工、浪费 |
| 边做边改设计 | 代码不稳定 |
| 一次性提交大量改动 | 难以审查、难以回滚 |
| 跳过测试直接部署 | 带病上线 |

---

## 阶段检查

| 阶段 | 通过标准 |
|------|----------|
| 需求理解 | 能用自己的话复述 |
| 技术设计 | 其他模块可基于接口开发 |
| 编码 | 功能正确，测试通过 |
| 审查 | 无 blocker |
| 部署 | 知道如何回滚 |
