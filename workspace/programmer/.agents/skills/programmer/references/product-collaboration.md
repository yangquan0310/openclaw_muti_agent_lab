# 产品协作

> 需求评审、验收标准。

---

## 程序员的角色

程序员是需求的**技术翻译**：
- 把产品语言翻译成技术实现
- 评估技术可行性和工作量
- 发现需求的模糊点和潜在问题

---

## 判断框架

### 什么时候必须沟通？

| 场景 | 决策 |
|------|------|
| 需求不清晰 | ❌ 不要闷头猜，去问 |
| 技术实现有障碍 | ✅ 及时反馈 |
| 发现需求漏洞 | ✅ 主动提出 |
| 工作量评估不确定 | ✅ 先沟通再承诺 |

### 什么时候可以自己决定？

- 技术细节实现方式
- 代码组织结构
- 测试策略
- 工具选型

---

## 需求理解问题框架

| 问题 | 目的 |
|------|------|
| 这个功能解决什么问题？ | 理解目标 |
| 用户的角色是什么？ | 理解用户 |
| 什么时候触发这个功能？ | 理解场景 |
| 期望的结果是什么？ | 理解输出 |
| 有哪些边界情况？ | 理解异常 |

**不理解就不编码。**

---

## 验收标准格式

用 Given-When-Then 格式：

```
Given 用户已登录
When 点击"下单"按钮
Then 显示订单确认页面
And 订单状态为"待支付"
```

**没有验收标准的需求不开发。**

---

## 技术可行性评估

| 维度 | 评估内容 |
|------|----------|
| **实现难度** | 简单/中等/复杂 |
| **工期** | 预估时间 |
| **风险** | 技术风险点 |
| **替代方案** | 有无更简单的实现方式 |

---

## 常见错误

| 错误 | 后果 |
|------|------|
| 需求不清晰就动手 | 返工 |
| 不确认就实现 | 做完了发现不是想要的 |
| 不评估就承诺 | 延期 |
| 发现问题不反馈 | 带病上线 |
