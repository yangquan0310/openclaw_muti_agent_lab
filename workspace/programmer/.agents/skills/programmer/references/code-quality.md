# 代码质量

> 好代码的标准。

---

## 核心标准

### 可读性

代码是写给人看的，顺便给机器运行。

**判断**：
- 他人能理解吗？
- 自己三个月后能理解吗？

### 可维护性

改起来容易，不影响其他模块。

**判断**：
- 改一个地方会不会引出三个新 bug？
- 新人能接手吗？

### 可测试性

容易写测试，测试能覆盖核心逻辑。

**判断**：
- 这个函数能单独测试吗？
- 依赖能 mock 吗？

## 命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 变量 | snake_case，描述内容 | `user_name`, `is_valid` |
| 函数/方法 | snake_case，动词开头 | `get_user()`, `validate_input()` |
| 类 | PascalCase，名词 | `UserService`, `OrderManager` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 模块 | 全小写 | `utils`, `auth` |

---

## 函数设计原则

| 原则 | 说明 |
|------|------|
| **单一职责** | 一个函数只做一件事 |
| **短小** | 理想 < 20 行 |
| **参数少** | 理想 < 3 个 |
| **无副作用** | 相同输入 → 相同输出 |

---

## 注释原则

| 需要注释 | 不需要注释 |
|----------|------------|
| 为什么这么做 | 代码本身能说明的 |
| 复杂逻辑 | 明显的逻辑 |
| 业务规则 | 追踪变更（用 git） |

---

## 不合格模式

| 模式 | 问题 |
|------|------|
| 过长函数 | 难以理解和测试 |
| 重复代码 | 改一处漏一处 |
| 神秘命名 | `temp`、`data`、`tmp` |
| 深层嵌套 | 超过 3 层需要重构 |
| 哑函数 | 只有 getter/setter 的类 |
