# 架构设计

> 什么时候设计、设计什么。

---

## 判断框架

### 什么时候必须做架构设计？

| 场景 | 决策 |
|------|------|
| 新项目 | 必须 |
| 新模块（影响范围大）| 必须 |
| 引入新的技术组件 | 必须 |
| Bug 修复 | 不需要 |
| 小功能改动 | 不需要 |

### 什么时候可以跳过架构设计？

- 单个模块内的局部改动
- 纯性能优化不改变结构
- 重命名/清理代码
- 测试补充

---

## 架构目标

| 目标 | 含义 |
|------|------|
| **可维护** | 改起来容易，不影响其他模块 |
| **可扩展** | 加新功能不需要改老代码 |
| **可测试** | 单元测试容易写 |
| **可部署** | 独立部署，不相互影响 |

---

## 常见架构模式

| 模式 | 适用场景 | 复杂度 |
|------|----------|--------|
| **分层架构** | 一般应用 | 低 |
| **MVC** | Web 应用 | 低 |
| **微服务** | 大型系统 | 高 |
| **CQRS** | 读写分离 | 中 |
| **DDD** | 复杂业务逻辑 | 高 |

---

## SOLID 原则

| 原则 | 说明 |
|------|------|
| **S** 单一职责 | 一个类只有一个变化原因 |
| **O** 开闭原则 | 对扩展开放，对修改关闭 |
| **L** 里氏替换 | 子类可替代父类 |
| **I** 接口隔离 | 接口要小而专 |
| **D** 依赖反转 | 依赖抽象，不依赖具体 |

## 分层架构参考

```
┌─────────────────┐
│    Controller   │  ← 处理请求
├─────────────────┤
│     Service     │  ← 业务逻辑
├─────────────────┤
│   Repository    │  ← 数据访问
├─────────────────┤
│      Model      │  ← 数据模型
└─────────────────┘
```

## 不合格模式

| 模式 | 问题 |
|------|------|
| 循环依赖 | A→B→C→A |
| 上帝类 | 一个类做所有事 |
| 无限扩展 | 老代码不敢改，新代码堆上面 |
| 耦合过紧 | 改一个模块影响一堆 |
