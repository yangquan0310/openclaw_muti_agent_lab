# 整理工作流

> 当用户要求"整理"某个项目时，执行的手动整理流程。

---

## 一、整理的本质

整理不是一键清理，而是**有目的地重组项目结构**。每个文件的移动都需要有理由，每个目录的创建都需要有用途。

整理前必须先明确：这个项目的类型是什么？它的标准结构应该是什么？当前结构和标准结构之间差什么？

---

## 二、核心原则

**已取消自动整理/一键整理功能**。大管家在收到"整理"指令时，按以下流程手动执行。

> ⚠️ **每次整理前必须先检查 TODO.md 状态**，确保任务看板与实际情况一致。整理后如影响项目进度，需同步更新 TODO.md。

---

## 三、完整流程

**第一步：检查现状**。查看当前目录结构、文件分布，检查 metadata.json 是否存在。这一步的目的是了解"现在是什么样"。

**第二步：识别类型**。判断属于 thesis/course/program/通用项目中的哪一种，然后调用对应的指南。这一步的目的是知道"应该是什么样"。

**第三步：确认需求**。拿捏不准时，向用户确认："这个项目有特殊文件需要保护吗？""XX文件/目录是否需要移动？"

**第四步：执行整理**。创建标准目录、按规则移动文件、更新 metadata.json。

**第五步：验证结果**。检查契约文件是否在根目录，保护文件是否未被动过，TODO.md 是否需要更新。

**第六步：汇报用户**。提醒用户维护好 TODO.md，输出整理摘要，列出所有变更。

---

## 四、按项目类型的整理要点

| 项目类型 | 专用目录 | 特殊文件 |
|----------|----------|----------|
| thesis | knowledge/, retrieval_report/ | Pandoc 文件 |
| course | syllabus/, chapters/, shared/ | 课件模板 |
| program | src/, test/, docs/ | .openclaw 旧目录 |
| 通用 | 无 | 无 |

---

## 五、需要确认的场景

| 场景 | 行动 |
|------|------|
| 存在 Pandoc 项目 | 询问用户是否保护 |
| 存在修改清单 | 询问用户是否保留 |
| 中文目录 vs 英文目录 | 询问用户偏好 |
| manuscripts/ 中有 README.md | 立即移回根目录，无需确认 |
| 存在未知类型的文件 | 询问用户处理方式 |
| 项目已有复杂结构 | 询问用户整理策略 |

---

## 六、禁止行为

- ❌ 不经确认删除任何文件
- ❌ 不经确认移动契约文件（README.md 等）
- ❌ 不检查 TODO.md 就执行整理
- ❌ 使用自动整理脚本
